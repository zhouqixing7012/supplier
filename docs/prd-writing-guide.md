# 供应商PRD写作规则

依据用户自行修订的《供应商系统优化PRD.docx》整理。写作规则来自实际删改；业务规则变化单独追踪，避免把文字删减解释成功能删除。

## 需求深度随实际改动量调整

- 每项保留问题描述、需求详情、涉及页面。问题写真实现象及具体阻碍，需求直接写改动。
- 简单修复聚焦改哪里、改成什么，必要时一条即可。例如评分联系人和部门恢复文本输入、分组标题换成业务名称。
- 已有且未受改动影响的查询、返回、失败重试、状态复核、重复提交等规则，不在每项机械展开。确实影响本次变化时再说明。
- 复杂业务保留必要字段、必填、枚举、状态、条件和校验。用户保留评分的合作类型、评分项、分值、切换确认和提交结果，也保留长期有效的日期校验。
- 界面改造需求聚焦本次问题：银行漏提交写待提交标签、数量汇总、固定提交入口，避免将整段银行维护流程重写。

## 用图承载界面差异

- 当前用户稿31项均配图，合计69处嵌入图实例。按场景使用现状/改造后对照、连续操作截图或不同类型截图；不是机械限定每项两张。
- 图片放在对应需求标题之后，正文说明问题、变化及必要规则。正文避免逐点复述图片已经清楚表达的纯界面细节。
- 不同类型的入口位置确有差异时，配图覆盖关键分支。例如注册邮箱覆盖四类供应商。

## 标题和结构方便评审

- 保留移动端、PC端线上问题、PC端新增优化需求三个章节。
- 标题使用实际问题或明确改造目标，例如导出增加引导步骤、协同门户增加工作台。
- 按用户决定标记P2及外系统，不能自行推断优先级。
- 同一问题相关动作合并，避免为通用规则重复立项。用户稿不再单列下拉统一、邀请人搜索、注册地址抽屉；资料编辑状态与取消归入具体修改需求。是否取消功能另看明确指示。
- 新稿编号为31项，主干旧稿为35项。按语义关联历史内容，不能只按相同编号对照。

## 精确描述操作与结果

- 使用业务页面实际字段和按钮名称，避免泛称组件、子表格等实现词。
- 写明确结果，如确认导出后浏览器下载文件、重新邀请后按本次邮件信息发送。
- 以现状为基础描述必要变化，避免将已有功能重新扩成新需求。
- 来源说明、分析过程、代码依据、技术联调及运维提示放评审记录，不放正式业务正文。

## 产品要求与UI方案分别处理

- 图标需求写联系人、银行、权限的业务含义及对应新增动作。当前原型的标题行文字按钮不是需求本身。
- 未定的图标、入口位置和diff样式交由UI设计，避免提前把标题行文字按钮、悬浮按钮或某种卡片排版写成唯一实现。
- 用户可用简短责任备注表达真实待设计事项；不据此向正文加入大量未确认的实现或补充建议。

## 生成前后自查

1. 本条实际改动是什么，是否能用更短的文字准确说明？
2. 每项细则是否服务于本次改动，还是重复描述现有流程？
3. 复杂需求的关键字段、状态、校验是否完整保留？
4. 图片是否能清楚说明现状和目标，是否覆盖关键分支？
5. 按钮、字段、入口及操作结果是否使用实际业务名称？
6. 是否擅自增加范围、优先级、UI限制或未确认的业务规则？
7. 正文与图片、前后章节是否一致？疑似旧文残留应指出，避免自动当作新决定。


## 完整功能 PRD 的组织

- 完整功能说明按业务任务分节。入口条件、字段、操作、校验、成功和失败结果集中在同一节，不另设全篇校验表让读者拼接。
- 公共字段只维护一处；复用页面引用该字段表，并在本节写清与该页面相关的差异。注册审批的首节点填写与后续审批分开说明。
- 查询条件、结果展示字段分别核对。同名或相近菜单的字段不互相套用，隐藏菜单的规则不迁入保留菜单。
- 用业务名称说明对象和动作。长段落按操作顺序拆分；需要对比状态或处理结果时用表格。删去重复句和无新增约束的套话，保留字段、枚举、长度、状态、校验及特殊场景。
- 代码证据、接口核对、实现差异放评审记录。影响业务验收的未确认规则在对应功能保留简短提示，不用改标题或移动位置掩盖缺口。
- 目录用于定位功能，不重复正文规则。历史需求稿保留追溯，现行规则只维护在正式 PRD。
